# 游戏王 OCG 规则问答系统（RAG）

基于《游戏王 OCG 大师规则》构建的规则问答系统：本地检索 + 精排 + 本地大模型生成，
答案带原文页码引用。**自带 198 道官方规则检定测试的评测集**，所有效果数字可复现。

> 一句话结论：检索增强在这套语料上带来了可测量的收益（+6.1 个百分点），但也暴露出
> 语料本身的覆盖边界 —— 详见[评测](#评测)。

## 关键数字

| 指标 | 数值 |
| --- | --- |
| 检索语料 | 597 个规则片段（349 页官方规则书，剔除目录与考卷后） |
| 评测集 | 245 道题，其中 198 道官方单选题可用（2018–2021 四套规则检定测试） |
| 最佳配置准确率 | **31.3%**（62/198），闭卷基线 25.3% |
| 精排提速 | 20 候选重排：CPU 53,320 ms → GPU **306 ms**（约 174×） |
| 端到端延迟 P50 | 1,269 ms（检索 306 ms + 生成 949 ms），全本地、零 API 成本 |

## 快速开始

```bash
# 1. 依赖（torch 走 CUDA 索引，requirements.txt 里已配好）
pip install -r requirements.txt

# 2. 原始资料（第三方文档，未入库，需自行下载）
#    下载 https://ocg-rule.readthedocs.io/zh-cn/latest/ 的 PDF
#    存为 data/ocg-rule-readthedocs-io-zh-cn-latest.pdf

# 3. 构建索引（幂等，可重复执行）
python build_vector_store.py

# 4. 提问
python query_rag.py
python query_rag.py --no-rerank     # 关闭精排做对比

# 5. 评测
python eval/parse_goldens.py        # 从 PDF 第 6 章解析出 goldens
python eval/run_eval.py             # 跑全部配置（可中断续跑）
python eval/run_eval.py --report    # 只出报告表

# 6. 测试
python tests/test_rag_core.py       # 引用校验逻辑，零依赖、秒级
```

还需要本地运行 [Ollama](https://ollama.com) 并拉取模型：`ollama pull qwen2.5:7b`。

## 架构

```
rag_core.py —— 应用与评测共用的检索核心（单一来源）
  ├─ 索引与模型常量、检索配置定义（MODES）
  ├─ 向量检索 / 交叉编码器精排(GPU) / 中文 BM25 与融合
  ├─ 证据编号与页码引用格式
  └─ 两种提示词模板（开放式问答 / 单选题）

建库（离线，幂等）
  PDF ──PyPDFLoader──► 切片(1000/200) ──► 角色判定 ──► 过滤 ──► bge-small-zh ──► Chroma
                                          │
                                          ├─ rule-doc   596  规则正文
                                          ├─ rule-note    1  补充笔记
                                          ├─ toc         27  ✗ 目录页，丢弃
                                          └─ rule-test   90  ✗ 考卷（含答案键），丢弃

问答（在线，query_rag.py）
  问题 ──► 向量粗召回 20 ──► bge-reranker-v2-m3 精排(GPU) ──► top3
                                                             │
                            带页码编号的上下文 ──► qwen2.5:7b ──► 流式答案 + [n] 引用

评测（eval/run_eval.py）
  同一批题目 × 5 种检索配置 ──► 单选题准确率 + McNemar 配对检验
```

`query_rag.py` 与 `eval/run_eval.py` **都不自己实现检索与提示词**，全部调用 `rag_core.py`。
这是刻意的约束：如果两条路径各写一份，评测就会在不知不觉中不再代表线上行为 ——
你测的是一个系统，上线的是另一个。

建库会写出 `chroma_db/manifest.json`，记录切片参数、来源文件 sha256、角色分布与
丢弃原因，构建结果自描述、可复查。

## 评测

评测集来源：规则书第 6 章自带 **2018 / 2019 / 2020 / 2021 四套 KONAMI 官方规则检定测试**
（单选，含官方答案键），另有 2017、2020 两套非官方规则测试。脚本自动解析题目、选项与
答案键；依赖图片作答的题、多选题、带「裁定变更」标注导致答案不唯一的题都已自动排除。

完整报告见 [`eval/report.md`](eval/report.md)（由脚本生成）。

| 配置 | 题数 | 准确率 | 检索 P50 | 端到端 P50 |
| --- | ---: | ---: | ---: | ---: |
| 闭卷（无检索·基线） | 198 | 25.3% (50/198) | — | 130 ms |
| 纯向量 top3 | 198 | 26.8% (53/198) | 8 ms | 919 ms |
| 纯向量 top8 | 198 | 28.8% (57/198) | 7 ms | 952 ms |
| **向量20 + rerank3** | 198 | **31.3% (62/198)** | 306 ms | 1,269 ms |
| BM25+向量融合 top3 | 198 | 26.3% (52/198) | 40 ms | 960 ms |

5 选 1 的随机水平是 20%，闭卷基线 25.3% 说明模型靠自身常识只能勉强高于乱猜。

**配对显著性检验（McNemar 精确检验，只看结论不同的题）：**

| 配置 | 检索后答对 | 检索后答错 | p 值 | 结论 |
| --- | ---: | ---: | ---: | --- |
| 纯向量 top3 | 19 | 16 | 0.736 | 不显著 |
| 纯向量 top8 | 23 | 16 | 0.337 | 不显著 |
| **向量20 + rerank3** | **27** | **15** | **0.088** | 趋势正向，未达 0.05 |
| BM25+向量融合 | 19 | 17 | 0.868 | 不显著 |

### 从评测里读出的三件事

1. **只有精排有稳定正向趋势。** 纯向量、混合检索相对闭卷基线的差异完全在噪声范围内；
   两阶段检索（粗召回 20 → 精排 3）是唯一同时提高准确率和改善逐题对比的配置。
   这也说明"加个 BM25 混合检索"在这套语料和题型下并不自动有效。
2. **55%（109/198）的题在所有配置下都答错。** 抽查这些题的题干可以看到，它们问的是
   **单卡的具体处理**（「禁止令」宣言卡名的怪兽能否解放、「巨大化」的攻击力计算、
   「No.89 电脑兽 系统破坏神」的效果能否发动……），而规则书只讲通用规则，
   **不含卡片文本与官方 Q&A**。因此这个上限是**语料覆盖问题，不是检索算法问题** ——
   要突破必须接入卡片数据库与官方 Q&A 语料。
3. **精排的开销是值得的。** 精排把检索耗时从 8 ms 提到 306 ms，但端到端只占 24%，
   而它是唯一带来正向收益的环节。

## 设计决策

**为什么把考卷整体剔除，而不是"检索时记得过滤"？**
规则书第 6 章是 6 套规则检定测试，**答案键原文就在里面**（形如 `1-5ADCBD`）。
把它们向量化进索引，等于每次检索都可能把标准答案递给模型；而用它做评测则构成数据泄漏，
测出来的是"抄答案"。所以这里在**入库阶段**就丢弃 `rule-test` 角色 ——
让正确的行为成为默认，而不是依赖人的纪律。评测集的题目因此不可能从索引里被检索到。

**为什么给片段打 role？**
同一份 PDF 里混着三种性质完全不同的内容：规则正文、目录页、考卷。
旧索引把 715 个片段不加区分地放进同一个向量空间，其中 27 条是不含信息量的目录点线
（`3.1.3 咒文速度 . . . . .29`），90 条是考卷。打上角色后，可检索语料从 715 降到 597。

**为什么切片是 1000 / overlap 200？**
规则书的论述逻辑连贯，500 字符会把"条件—例外—处理"切断，检索到半句话反而误导模型。
overlap 200 保证跨片段的规则衔接不丢。分隔符列表优先按段落和中文标点切。

**为什么答案要带页码引用？**
`page_label` 从一开始就存在元数据里，但旧版从不返回给用户 —— 用户无法核对，
模型说错也看不出来。现在每段资料带 `[n] 规则书 p.xxx` 编号，模型被要求用 `[n]` 标注依据，
并要求在资料不足时明确拒答。

**为什么引用要做服务端校验？**
因为模型会编造编号。实测问「灰流丽能否在伤害步骤发动」时，答案写了「根据参考资料 [1] 和 [4]」，
而提示词里只给了 3 段资料 —— 用户看到编号会以为有据可查，实际指向空气。
现在每轮问答结束后由 `rag_core.check_citations()` 把答案里的编号与本次提供的资料段数比对，
越界编号**显式告警**，并在依据清单里标出哪几段被真正引用、哪几段没被用上。

这里刻意**只校验、不修改答案**：把越界编号删掉并不会让那句话变正确，
告诉用户"这处依据无法核实"才是诚实的处理。

校验器本身也踩过坑并用测试锁住了：模型会照抄资料里的章节标题（如 `[4.4. 战斗阶段流程 144]`），
最初的解析器把标题里的页码 144 误判成引用编号，产生假告警。
现在只接受"括号内仅有数字与分隔符"的写法，`tests/test_rag_core.py` 里有对应的回归用例。

**为什么要流式和分段计时？**
旧版每问要等 50 秒以上才一次性吐出结果，用户无法判断是在检索、在重排还是在生成。
现在输出流式打印，并在每轮结束时显示"检索 X ms / 生成 Y ms"，
把瓶颈直接暴露出来（这也是发现精排跑在 CPU 上的原因）。

**为什么抽 `rag_core.py` 共享模块？**
应用和评测一旦各写一份检索逻辑，就会悄悄跑偏：你测的是一个系统，上线的是另一个。
抽取时用 40 条提示词快照（8 题 × 5 配置）**逐字节比对**，确认重构前后完全一致 ——
因此 `eval/results/` 下已发布的 990 条记录仍然可由当前代码复现，重构没有让任何历史数字失效。

## 已知限制

- **准确率绝对值不高（31.3%）**：题型是官方检定测试的应用题，语料缺卡片与官方 Q&A，
  这是当前语料的上限，不是提示词问题。下一步应接入卡片数据与官方 Q&A。
- **索引片段仍带 PDF 页眉页脚**：实测 597 个片段中 **551 个（92.3%）含
  `ocg-rule Documentation` 页眉或「章节号 + 标题 + 页码」页脚**，合计占 2.21% 字符。
  字符开销不大，但它有两个实际害处：一是这些样板文字会被向量编码进去，
  二是模型会把章节标题当成引用内容照抄（上面那个误报就是这么来的）。
  修法是在建库阶段加清洗并重建索引，代价是评测数字需要重跑。
- **规则版本敏感性**：规则书含历年裁定变更，检索不带时间维度，
  问"某年某规则"时可能取到不同年份的表述。
- **未做多轮对话**：规则追问（"那如果是速攻魔法呢"）需要指代消解，当前每问独立。
- **单库单语言**：仅中文语料。
- `langchain-community` 已被上游标记 sunset，`PyPDFLoader` 会打 DeprecationWarning，
  后续可迁移到独立集成包（功能不受影响）。

本项目在架构设计上参考了 [coldiceh/ocg-ruling-assistant](https://github.com/coldiceh/ocg-ruling-assistant)
（MIT License）的公开实现与文档。**没有复制任何代码** —— 对方是 JavaScript/Node（424 个 `.mjs`），
本项目是 Python，语言层面就不存在可复用的一行。借鉴的是以下通用工程做法：

- 给语料片段标注"角色"（`rule-doc` / `rule-test` / `toc` / `site-info`），把考卷与目录整体
  排除出检索 —— 连角色命名也沿用了该项目的分类
- 构建产物写出 manifest，记录来源哈希、切片参数与角色分布，使构建结果可复查
- 引用必须可追溯到具体来源，模型不得自由编造出处
- 用评测集而不是主观感受来判断每次改动是否有效

**本项目独立完成的部分**

- `eval/parse_goldens.py`：从 PDF 第 6 章直接解析题目、选项与答案键。
  （对方走的是 HTML 结构化解析 + 官方 Q&A 语料，技术路线不同，本项目也没有那套语料）
- `eval/run_eval.py`：5 种检索配置的准确率对比 + McNemar 配对显著性检验
- 以下实测结论为本项目独有：闭卷基线 25.3%、精排相对基线 +6.1 个百分点（p=0.088）、
  109/198 道题在所有配置下均错且归因为**语料缺少卡片文本与官方 Q&A**，而非检索算法问题
