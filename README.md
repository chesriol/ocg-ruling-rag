# 游戏王 OCG 规则问答系统（RAG）

基于《游戏王 OCG 大师规则》构建的规则问答系统：本地检索 + 精排 + 本地大模型生成，
答案带原文页码引用。**自带 198 道官方规则检定测试的评测集**，所有效果数字可复现。

> 一句话结论：检索增强在这套语料上带来了可测量的收益（+6.1 个百分点），但也暴露出
> 语料本身的覆盖边界 —— 详见[评测](#评测)。

## 关键数字

| 指标 | 数值 |
| --- | --- |
| 检索语料 | 578 条规则片段 + 15,019 张卡片文本（卡名精确匹配）+ 2,122 条官方 Q&A |
| 语料清洗 | 删除 338 处页眉、337 处页脚（占原字符 2.21%） |
| 评测集 | 245 道题，其中 198 道官方单选题可用（2018–2021 四套规则检定测试） |
| 最佳配置准确率 | **32.8%**（65/198，McNemar p=0.024 **显著**），闭卷基线 25.3% |
| **推理噪声下限** | 同配置重复三次：24.2% / 25.3% / 25.8% —— 约 **±1.5 道题**，小于此的差异不可信 |
| 精排提速 | 20 候选重排：CPU 53,320 ms → GPU **306 ms**（约 174×，同源语料对比） |
| 端到端延迟 P50 | 2,911 ms（检索 575 ms + 生成 2,263 ms）—— 加语料后显著变慢，原因见[已知限制](#已知限制) |

## 快速开始

```bash
# 1. 依赖（torch 走 CUDA 索引，requirements.txt 里已配好）
pip install -r requirements.txt

# 2. 原始资料（均为第三方内容，未入库，用脚本下载）
python fetch_cards.py          # 中文卡片数据库（zh-CN + zh-SC，约 14 MB）
python fetch_qa.py             # 官方规则 Q&A（约 20 分钟，见下文说明）
#    规则书 PDF 需手动下载 https://ocg-rule.readthedocs.io/zh-cn/latest/
#    存为 data/ocg-rule-readthedocs-io-zh-cn-latest.pdf

# 3. 构建索引（幂等，可重复执行）
python build_vector_store.py

# 4. 提问
python query_rag.py
python query_rag.py --no-rerank                    # 关闭精排做对比
python query_rag.py --mode vector_rerank_cards_qa  # 卡片 + 规则 + 官方 Q&A

# 5. 评测
python eval/parse_goldens.py        # 从 PDF 第 6 章解析出 goldens
python eval/run_eval.py             # 跑全部配置（可中断续跑）
python eval/run_eval.py --report    # 只出报告表

# 6. 测试
python tests/test_rag_core.py       # 引用校验逻辑，零依赖、秒级
```

还需要本地运行 [Ollama](https://ollama.com) 并拉取模型：`ollama pull qwen2.5:7b`。

## 架构

```
rag_core.py —— 应用与评测共用的检索核心（单一来源）
  ├─ 索引与模型常量、检索配置定义（MODES）、角色过滤（role）
  ├─ 向量检索 / 交叉编码器精排(GPU) / 中文 BM25 与融合
  ├─ 证据编号与来源标签格式
  └─ 两种提示词模板（开放式问答 / 单选题）
card_index.py —— 卡片文本：卡名精确匹配取卡文（刻意不进向量库）

建库（离线，幂等）
  PDF ──PyPDFLoader──► 清洗页眉页脚 ──► 切片(1000/200) ──► 角色判定 ──► 过滤 ──► 向量化 ──► Chroma
                       (338 页眉 / 337 页脚)                  │
                                                              ├─ rule-doc      577  规则正文
                                                              ├─ rule-note       1  补充笔记
                                                              ├─ official-qa  2122  官方 Q&A（见下）
                                                              ├─ toc            27  ✗ 目录页，丢弃
                                                              └─ rule-test      86  ✗ 考卷（含答案键），丢弃

卡片库（离线，独立于向量库）
  cards-zh-CN.cdb ─┐
                   ├─► CardIndex：24,178 个别名 → 15,019 张卡文（覆盖 65.2% 的评测题）
  cards-zh-SC.cdb ─┘

问答（在线，query_rag.py）
  问题 ──┬─► 向量粗召回 20 ──► bge-reranker-v2-m3 精排(GPU) ──► top3 规则片段
         ├─► 「」卡名识别 ──► 精确取卡片文本 ──► 最多 6 张
         └─► 官方 Q&A 检索（role=official-qa 过滤）──► top3
                                        │
               统一编号的证据（卡片 + 规则 + Q&A）──► qwen2.5:7b ──► 流式答案 + [n] 引用校验

评测（eval/run_eval.py）
  同一批题目 × 9 种检索配置 ──► 单选题准确率 + McNemar 配对检验
```

**角色过滤是隔离带**：既有配置只看 `rule-doc` / `rule-note`，新配置才纳入 `official-qa`。
这样"新增语料"不会悄悄改掉历史配置的行为，消融才有意义。

`query_rag.py` 与 `eval/run_eval.py` **都不自己实现检索与提示词**，全部调用 `rag_core.py`。
这是刻意的约束：如果两条路径各写一份，评测就会在不知不觉中不再代表线上行为 ——
你测的是一个系统，上线的是另一个。

建库会写出 `chroma_db/manifest.json`，记录切片参数、来源文件 sha256、角色分布与
丢弃原因，构建结果自描述、可复查。

## 评测

评测集来源：规则书第 6 章自带 **2018 / 2019 / 2020 / 2021 四套 KONAMI 官方规则检定测试**
（单选，含官方答案键），另有 2017、2020 两套非官方规则测试。脚本自动解析题目、选项与
答案键；依赖图片作答的题、多选题、带「裁定变更」标注导致答案不唯一的题都已自动排除。

完整报告见 [`eval/report.md`](eval/report.md)（由脚本生成）。

| 配置 | 题数 | 准确率 | 检索 P50 | 端到端 P50 |
| --- | ---: | ---: | ---: | ---: |
| 闭卷（无检索·基线） | 198 | 25.3% (50/198) | — | 140 ms |
| 纯向量 top3 | 198 | 28.8% (57/198) | 267 ms | 2,379 ms |
| 纯向量 top8 | 198 | 30.8% (61/198) | 24 ms | 2,068 ms |
| 向量20 + rerank3（仅规则） | 198 | 31.8% (63/198) | 637 ms | 2,737 ms |
| BM25+向量融合 top3 | 198 | 25.8% (51/198) | 230 ms | 2,666 ms |
| 仅卡片文本 | 198 | 29.8% (59/198) | 3 ms | 291 ms |
| rerank3 + 卡片文本 | 198 | 30.8% (61/198) | 674 ms | 2,970 ms |
| 仅官方 Q&A | 198 | 29.8% (59/198) | 686 ms | 2,398 ms |
| **rerank3 + 卡片 + 官方Q&A** | 198 | **32.8% (65/198)** | 575 ms | 2,911 ms |

5 选 1 的随机水平是 20%，闭卷基线 25.3% 说明模型靠自身常识只能勉强高于乱猜。

**配对显著性检验（McNemar 精确检验，只看结论不同的题）：**

| 配置 | 检索后答对 | 检索后答错 | p 值 |
| --- | ---: | ---: | ---: |
| 纯向量 top3 | 22 | 15 | 0.324 |
| 纯向量 top8 | 26 | 15 | 0.117 |
| 向量20 + rerank3 | 26 | 13 | 0.053 |
| BM25+向量融合 | 16 | 15 | 1.000 |
| 仅卡片文本 | 18 | 9 | 0.122 |
| rerank3 + 卡片文本 | 27 | 16 | 0.126 |
| 仅官方 Q&A | 21 | 12 | 0.163 |
| **rerank3 + 卡片 + 官方Q&A** | **27** | **12** | **0.024 ✅ 显著** |

**这是整个项目里第一个达到 p<0.05 的结果**：规则 + 卡片 + 官方 Q&A 三者叠加后，
相对闭卷基线的提升（+15 道题）已经不太可能用噪声解释。

### ⚠️ 先看这个：推理噪声下限（它决定了上面所有数字怎么读）

做卡片消融时发现一个内部矛盾：有些题目识别不出任何卡片，`cards_only` 与 `closed_book`
**生成的提示词逐字节相同**，模型却给出了不同答案。于是把同一个配置重跑了三次：

| 重复次数 | 准确率 | 与第一次预测不同的题 |
| --- | ---: | ---: |
| 第一次 | 50/198 · 25.3% | — |
| 第二次 | 48/198 · 24.2% | 11 道（5.6%） |
| 第三次 | 51/198 · 25.8% | 9 道（4.5%） |

**结论：`temperature=0` 并不等于确定性。** 同一份提示词、同一个模型，
三次结果有 12 道题（6.1%）不完全一致，准确率波动 ±1.5 道题。

**这把全部结论重新校准了** —— 任何小于 ±1.5 道题的差异都不能当结论：

| 对比 | 差异 | 判定 |
| --- | ---: | --- |
| 闭卷(50) → rerank3(63) | 13 道题 | ✅ 超出噪声，可信 |
| rerank3(63) → rerank3+卡片(61) | −2 道题 | ⚠️ 噪声内（卡片单独看不出收益） |
| rerank3+卡片(61) → +官方Q&A(65) | **+4 道题** | ✅ 刚超出噪声（逐题 12 对 / 8 错） |
| 闭卷(50) → rerank3+卡片+Q&A(65) | **15 道题** | ✅ 显著（p=0.024） |
| 清洗页眉页脚前后 | ≤4 道题 | ⚠️ 噪声内，解释了当时为什么"有升有降" |

**所以要检测 1~2 道题量级的差异，必须提高统计功效**：扩大评测集，
或对每题重复多次取多数票降方差（`--results-dir` 就是为此留的）。

> 经验：如果你的评测集只有一两百题、而模型推理本身有 5% 的抖动，
> 那么"提升 1~2 个百分点"这类结论基本没有意义。**先量噪声，再谈提升。**

### 卡片语料消融（提升是否真的来自卡片）

按"题目里能否识别出卡片"分组——如果卡片真的起作用，提升应该集中在有卡片的那一组：

| 分组 | 题数 | 闭卷 | rerank3（仅规则） | 仅卡片 | rerank3 + 卡片 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 有卡片可识别 | 129 | 26.4% | 32.6% | 29.5% | 33.3% |
| 无卡片可识别 | 69 | 23.2% | 30.4% | 29.0% | 26.1% |

- 有卡片组上"卡片+规则"最高，符合假设方向；无卡片组上"仅卡片"接近闭卷，
  说明那点差异来自噪声而非卡片本身。
- 卡片单独看只有 +2 道题（**在噪声内**），它的价值是在规则检索之上叠加时体现的。

### 官方 Q&A 消融（本轮唯一达到显著的一步）

同一个索引、同一批题目，只改"要不要检索官方 Q&A"：

| 配置 | 准确率 | 相对上一级 |
| --- | ---: | ---: |
| 闭卷（基线） | 50/198 · 25.3% | — |
| rerank3（仅规则） | 63/198 · 31.8% | +13 道 ✅ 超出噪声 |
| rerank3 + 卡片 | 61/198 · 30.8% | −2 道 ⚠️ 噪声内 |
| **rerank3 + 卡片 + 官方Q&A** | **65/198 · 32.8%** | **+4 道 ✅ 超出噪声（12 对 / 8 错）** |

- 单看 Q&A：仅官方 Q&A 就有 29.8%（+9 道），说明这块语料本身含有可回答问题的裁定。
- **变对的 12 道题正是官方 Q&A 该解决的类型**：连锁结算（「超魔导龙骑士」连锁 1/2 的处理）、
  效果适用范围（「雪暴」无效化的范围）、跨卡引用（「元素英雄 神·新宇侠」得到效果后不能再做什么）。
  规则书回答不了这些，卡片文本也回答不了 —— 它们问的是"两张卡这样交互怎么结算"。
- 上下文条数 6~12 条（卡片最多 6 + 规则 3 + Q&A 3），确认 Q&A 证据确实进入了提示词。

### 从评测里读出的四件事

1. **三类证据按数据性质分工，叠加后首次达到统计显著**（32.8%，p=0.024）。
   规则书管"通用规则"，卡片文本管"这张卡是什么效果"，官方 Q&A 管"这样交互怎么结算"。
2. **单看每一步，只有规则检索和官方 Q&A 的增益超出噪声**；卡片文本单独看是噪声级，
   它的作用是在组合里补充模型没有的卡文信息。
3. **95/198（48%）的题在所有配置下都答错**（接入 Q&A 前是 101 道）。
   剩余失败集中在需要**跨卡判例与完整场景推理**的题 —— 靠继续堆语料收益递减，
   下一步更该做的是提高统计功效（重复取多数票）或换更强的生成模型。
4. **加语料有明显的延迟代价**：把 2,122 条 Q&A 放进同一个 Chroma 集合后，
   规则检索的 P50 从 7 ms 涨到 267 ms（38 倍）—— 因为角色过滤是"先取候选再过滤"，
   集合越大，为满足过滤要捞的候选越多。**正确但慢**；生产上应按角色分集合建索引。

### 一次负结果：清洗页眉页脚没有提升准确率

建库时清洗了 338 处页眉、337 处页脚（原字符的 2.21%），然后**重建索引并重跑了全部 990 次生成**。
实验对照很干净：`closed_book` 配置完全不读索引，前后必须一致 —— 实测**都是 50/198**，
证明这轮唯一的变量确实只有语料。

| 配置 | 清洗前 | 清洗后 | 变化 |
| --- | ---: | ---: | ---: |
| 闭卷（基线，不读索引） | 50/198 25.3% | 50/198 25.3% | ±0 |
| 纯向量 top3 | 53/198 26.8% | 57/198 28.8% | +2.0 pp |
| 纯向量 top8 | 57/198 28.8% | 53/198 26.8% | −2.0 pp |
| 向量20 + rerank3 | 62/198 31.3% | 60/198 30.3% | −1.0 pp |
| BM25+向量融合 | 52/198 26.3% | 53/198 26.8% | +0.5 pp |

**结论：没有可测量的提升。** 各项配置有升有降，逐题看也是双向翻转
（如精排：修好 5 道、弄坏 7 道），"所有配置都答错"的题数从 109 只降到 108 ——
后来测出的**±1.5 道题噪声下限**正好解释了当时为什么看起来"有升有降"。

**这个负结果本身有价值**：它说明 2.21% 的样板文字不是这套系统的瓶颈，
真正卡住准确率的是语料覆盖。清洗仍然该做 —— 它消除了一个**已知的错误模式**
（模型把页脚当正文照抄成引用），也让语料更干净，但**不应该把它当成准确率优化的手段**。

> 经验：先量化噪声占比与推理噪声，再决定要不要为一次改动重建索引并重跑评测。
> 2% 的字符噪声换不来准确率，但如果一开始不做对照实验，很容易误以为"清洗肯定有用"。

## 官方 Q&A 语料：数据源调研

上一版的结论是"剩余失败集中在需要官方 Q&A 的多卡交互题"。补这块语料时，先做了数据源调研，
**过程本身有几个值得记录的发现**：

| 问题 | 实测结果 |
| --- | --- |
| 官网能直接爬吗？ | **不能**。`www.db.yugioh-card.com` 是 JS 渲染的 SPA，`faq_search.action` 返回的 77 KB HTML 里没有问答正文，内容全靠 AJAX 加载 |
| 官方有中文 Q&A 吗？ | **没有**。`request_locale=zh-CN` 的 FAQ 接口返回与日语版同尺寸的页面外壳，不含「質問/回答」；`request_locale=ja` 才有完整问答 |
| 有机器可读的镜像吗？ | 有。[db.ygoresources.com](https://db.ygoresources.com) 提供 JSON（`/data/qa/{id}`），参考项目也用它 |
| 镜像有中文吗？ | **没有**。`qaData` 的语言分支只有 `{ja, en}`；`/data/idx/card/name/zh` 是 404 |
| 有批量清单吗？ | **没有**。`/manifest/1` 是前端缓存清单；Q&A id 只能通过每张卡的 `qaIndex` 字段收集 |

**所以官方裁定语料必然是日文。** 唯一的本地化手段是把正文里的 `<<卡片内部id>>` 占位符
换成中文卡名 —— 卡名是裁定问题里信息量最大的部分。中文卡名取自镜像自己的
`/data/idx/card/name/cn`（7,461 条，一次请求拿全），实测占位符本地化率 **82.3%**
（查不到的名字保留原 id，不编造）。

**枚举与抽样**：没有批量接口，全量需要 2.3 万次卡片请求加数万次 Q&A 请求
（实测 0.85 秒/次，总计 10 小时以上）。因此对卡表做**等距抽样**（每 10 张取 1 张）：

```
卡表 7,461 张 → 抽样 746 张 → 收集到 2,084 个 Q&A id → 成功抓取 2,078 条 → 切成 2,122 条片段
```

抽样规则只看卡表顺序、**与评测集无关**——否则知识库就成了针对测试集的定制语料，
测出来的提升不代表真实能力。**代价要说清楚：这是约 10% 的全量语料，不是完整语料。**

> 另一个值得记录的工程细节：把 2,122 条 Q&A 向量加入同一个 Chroma 集合后，
> **既有配置的检索结果并非 100% 不变**。实测 32 条快照里 30 条逐字节一致，
> 2 条在 `vector_deep`（top-8）的边界处发生了近似并列项的位置交换 ——
> 因为 Chroma 用 HNSW 近似检索，加向量会改变图结构，而带 `where` 的角色过滤是
> "先取候选再过滤"，**过滤检索 ≠ 在更小的索引里检索**。
> 影响仅限于边界名次（7/8 片段相同），但足以说明：**新增语料后应当整表重跑，不要混用新旧索引的数字。**

## 设计决策

**为什么把考卷整体剔除，而不是"检索时记得过滤"？**
规则书第 6 章是 6 套规则检定测试，**答案键原文就在里面**（形如 `1-5ADCBD`）。
把它们向量化进索引，等于每次检索都可能把标准答案递给模型；而用它做评测则构成数据泄漏，
测出来的是"抄答案"。所以这里在**入库阶段**就丢弃 `rule-test` 角色 ——
让正确的行为成为默认，而不是依赖人的纪律。评测集的题目因此不可能从索引里被检索到。

**为什么给片段打 role？**
同一份 PDF 里混着三种性质完全不同的内容：规则正文、目录页、考卷。
旧索引把 715 个片段不加区分地放进同一个向量空间，其中 27 条是不含信息量的目录点线
（`3.1.3 咒文速度 . . . . .29`），90 条是考卷。打上角色后，可检索语料从 715 降到 597。

**为什么要清洗页眉页脚？**
PDF 每页都带页眉 `ocg-rule Documentation` 和页脚「`4.4. 战斗阶段流程 144`」。
清洗前实测 **597 个片段里 551 个（92.3%）带着这些样板文字**，合计占 2.21% 字符。
字符开销不大，但害处具体：这些文字会被向量编码进去，而且**模型会把章节标题当正文照抄** ——
实测它两次写出「根据参考资料 [1] 和 [4.4. 战斗阶段流程 144]」，把页脚当成了引用。

清洗的关键是**不要用模糊正则**：直接删「以数字开头、以数字结尾」的行会误删正文。
这里利用了一个已验证的事实 —— 实测 349 页共 343 处页脚，其中 **337 处的行尾数字恰好等于本页
`page_label`**（其余 6 处在罗马数字前言页，本就不入索引），于是**只在行尾数字等于本页页码时才删**，
零误删。清洗后片段数 597 → 578，页眉页脚残留为 0。

**清洗有效吗？** 消除了噪声，但**没有提升准确率** —— 重建索引并重跑 990 次生成后，
各配置有升有降、逐题双向翻转，特征与噪声一致（详见[评测](#一次负结果清洗页眉页脚没有提升准确率)）。
这个负结果把"什么是瓶颈"问清楚了：不是 2% 的样板文字，而是语料缺卡片与官方 Q&A。
清洗作为**消除已知错误模式**的手段保留，但不作为准确率优化的手段。

**为什么切片是 1000 / overlap 200？**
规则书的论述逻辑连贯，500 字符会把"条件—例外—处理"切断，检索到半句话反而误导模型。
overlap 200 保证跨片段的规则衔接不丢。分隔符列表优先按段落和中文标点切。

**为什么答案要带页码引用？**
`page_label` 从一开始就存在元数据里，但旧版从不返回给用户 —— 用户无法核对，
模型说错也看不出来。现在每段资料带 `[n] 规则书 p.xxx` 编号，模型被要求用 `[n]` 标注依据，
并要求在资料不足时明确拒答。

**为什么引用要做服务端校验？**
因为模型会编造编号。实测问「灰流丽能否在伤害步骤发动」时，答案写了「根据参考资料 [1] 和 [4]」，
而提示词里只给了 3 段资料 —— 用户看到编号会以为有据可查，实际指向空气。
现在每轮问答结束后由 `rag_core.check_citations()` 把答案里的编号与本次提供的资料段数比对，
越界编号**显式告警**，并在依据清单里标出哪几段被真正引用、哪几段没被用上。

这里刻意**只校验、不修改答案**：把越界编号删掉并不会让那句话变正确，
告诉用户"这处依据无法核实"才是诚实的处理。

校验器本身也踩过坑并用测试锁住了：模型会照抄资料里的章节标题（如 `[4.4. 战斗阶段流程 144]`），
最初的解析器把标题里的页码 144 误判成引用编号，产生假告警。
现在只接受"括号内仅有数字与分隔符"的写法，`tests/test_rag_core.py` 里有对应的回归用例。

**为什么要流式和分段计时？**
旧版每问要等 50 秒以上才一次性吐出结果，用户无法判断是在检索、在重排还是在生成。
现在输出流式打印，并在每轮结束时显示"检索 X ms / 生成 Y ms"，
把瓶颈直接暴露出来（这也是发现精排跑在 CPU 上的原因）。

**为什么抽 `rag_core.py` 共享模块？**
应用和评测一旦各写一份检索逻辑，就会悄悄跑偏：你测的是一个系统，上线的是另一个。
抽取时用 40 条提示词快照（8 题 × 5 配置）**逐字节比对**，确认重构前后完全一致 ——
因此 `eval/results/` 下已发布的记录仍然可由当前代码复现，重构没有让任何历史数字失效。
加入卡片证据时又做了一次同样的回归（40/40 一致），既有配置的提示词一个字节都没变。

**为什么卡片文本不进向量库？**
中文卡库有 1.5 万张卡。全部向量化会淹没规则片段，而且卡名是**精确匹配**问题 ——
问题里写「灰流丽」就是「灰流丽」，用向量近似去猜只会更差。
所以 `card_index.py` 单独成层：从问题里识别卡名（先取 `「」` 引号内容，再补无引号提及），
精确取出卡片文本，作为额外证据与规则片段一起编号。
这也让卡片证据的耗时只有 **2 ms**，几乎不影响端到端延迟。

**为什么官方 Q&A 反而进向量库？**
它和卡片文本相反：Q&A 是"问题↔答案"的自由文本，用户提问的措辞与官方 Q&A 的措辞
不会精确相同，**这正是语义检索该解决的问题**。而且它是裁定语料的核心 ——
规则书回答"通用规则是什么"，Q&A 回答"这两张卡这样交互时怎么结算"。
卡片（精确匹配）走独立层、Q&A（语义匹配）走向量层，是按数据性质分工，不是随意选择。

**为什么要做角色过滤？**
新增语料最大的风险不是"没效果"，而是**悄悄改掉了既有配置的行为**，让历史数字失去可比性。
`RULE_FILTER` / `QA_FILTER` 把"新增语料"和"改动既有配置"隔开：
既有配置只看 `rule-doc`/`rule-note`，新配置才纳入 `official-qa`。
每次加语料都会用检索快照逐条比对，确认既有路径未变
（这也正是发现 HNSW 边界扰动的那次检查）。

## 已知限制

- **准确率绝对值不高（32.8%）**：题型是官方检定测试的应用题。
  三类语料（规则书 / 卡片文本 / 官方 Q&A）都已接入，48% 的题仍在所有配置下答错 ——
  剩余失败集中在需要**跨卡判例与完整场景推理**的题。继续堆同类语料收益递减，
  下一步更有价值的是提高统计功效（重复取多数票）或换更强的生成模型。
  （已用对照实验排除三类干扰因素：清洗页眉页脚这类语料噪声、单纯加大上下文条数、
  以及"新语料改动了既有配置"。）
- **官方 Q&A 是抽样语料，不是全量**：没有批量接口，全量需要 10 小时以上抓取，
  当前是**对卡表等距抽样的约 10%**（746 张卡 → 2,078 条 Q&A）。
  抽样规则与评测集无关，但覆盖面确实有限。
- **官方 Q&A 是日文正文 + 中文卡名**：实测官方数据库没有中文 Q&A（`request_locale=zh-CN`
  的 FAQ 接口不含问答内容），镜像的语言分支只有 `{ja, en}`。当前用中文卡名替换
  `<<卡片内部id>>` 占位符做本地化（覆盖率 82.3%）。**这是一个折中，不是完美方案** ——
  彻底的解法是换多语言 embedding 模型，但那会同时改动全部向量，引入新的混淆变量。
- **加语料带来明显延迟代价**：2,122 条 Q&A 与规则片段混在同一 Chroma 集合，
  角色过滤是"先取候选再过滤"，规则检索 P50 从 7 ms 涨到 267 ms。
  正确但慢，生产上应按角色分集合建索引（本项目的取舍是保持单一索引、便于消融对比）。
- **统计功效不足**：198 道题 + 约 5% 的推理抖动，使**小于 ±1.5 道题的差异无法与噪声区分**。
  卡片文本带来的 +3 道题就落在这一区间内，因此只报"方向一致"，不报"已验证"。
- **规则版本敏感性**：规则书含历年裁定变更，检索不带时间维度，
  问"某年某规则"时可能取到不同年份的表述。
- **未做多轮对话**：规则追问（"那如果是速攻魔法呢"）需要指代消解，当前每问独立。
- **单库单语言**：仅中文语料。
- `langchain-community` 已被上游标记 sunset，`PyPDFLoader` 会打 DeprecationWarning，
  后续可迁移到独立集成包（功能不受影响）。

**架构思路参考**

本项目在架构设计上参考了 [coldiceh/ocg-ruling-assistant](https://github.com/coldiceh/ocg-ruling-assistant)
（MIT License）的公开实现与文档。**没有复制任何代码** —— 对方是 JavaScript/Node（424 个 `.mjs`），
本项目是 Python，语言层面就不存在可复用的一行。借鉴的是以下通用工程做法：

- 给语料片段标注"角色"（`rule-doc` / `rule-test` / `toc` / `site-info`），把考卷与目录整体
  排除出检索 —— 连角色命名也沿用了该项目的分类
- 构建产物写出 manifest，记录来源哈希、切片参数与角色分布，使构建结果可复查
- 引用必须可追溯到具体来源，模型不得自由编造出处
- 用评测集而不是主观感受来判断每次改动是否有效

**本项目独立完成的部分**

- `eval/parse_goldens.py`：从 PDF 第 6 章直接解析题目、选项与答案键。
  （对方走的是 HTML 结构化解析 + 官方 Q&A 语料，技术路线不同）
- `eval/run_eval.py`：9 种检索配置的准确率对比 + McNemar 配对显著性检验
- `card_index.py`：中文卡库的卡名精确匹配与证据注入
- `fetch_qa.py`：官方 Q&A 的抓取管线（含来源调研结论、等距抽样、日文正文的中文卡名本地化）
- 以下实测结论为本项目独有：闭卷基线 25.3%、三类语料叠加后 32.8%（p=0.024 显著）、
  规则检索 +13 道题 vs 卡片文本 −2 道题（**只有前者超出噪声**）、
  48% 的题在所有配置下均错，以及三个经过对照实验确认的方法论结论 ——
  "清洗页眉页脚不提升准确率"、"temperature=0 并非确定性，噪声下限约 ±1.5 道题"、
  "角色过滤能隔离改动但会让过滤检索变慢 38 倍"
